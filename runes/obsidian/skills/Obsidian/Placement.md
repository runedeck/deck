# Placement

Read this when deciding where a note belongs and what it should link to.
A useful existing folder can remain unchanged when only relationships need repair.

## Describe each affected note

Create one review record per note in the change report.
Use these fields without adding them as mandatory vault properties:

```text
Identity: Exact current path, title, aliases, and intended role.
Purpose: What a person expects to find or do in this note.
Home: Current path, proposed path, and routing reason.
Topic links: Existing concepts supported by the subject.
Work links: Project that uses the guide or owns the active work.
Reference links: Relevant resources, sources, artwork, and actual ingredients.
Membership: Existing collection, shelf, or other supported membership.
Metadata: Kept, removed, and changed fields with dependency reasons.
Expected views: Base path, view name, embedding context, and intended membership.
Preservation: Content, assets, provenance, logs, and incoming references affected.
```

Resolve identity questions before finalizing a target.
Choose a physical home using current vault routing and human browsing needs.
Create a folder only when it improves that route and matches the vault's conventions.
Do not substitute graph links for an understandable physical home.

## Keep roles clear

A topic represents a concept shared across work and references.
A project owns active tasks, decisions, progress, and operational logs.
A resource contains reusable knowledge and navigation after a particular project ends.
A collection groups typed records under its existing membership contract.
An inventory record describes an item. A recipe links only to items it actually uses.

These roles describe purpose. They do not prescribe identical tags across vaults.
One mixed note can require a project and resource split.
Do not copy recipe text into both merely to fill the new notes.
Keep each recipe in one authoritative note and link to it from useful entry points.

## Choose meaningful links during placement

Use the vault's established meanings for properties and body links.
For example, use `keywords` for topics where working notes establish that convention.
An existing vault can also use `keywords` for a project relationship. Inspect its examples first.
Use `related` for relevant companion records where that meaning is established.
Preserve `collection` membership rather than replacing it with a generic relationship.
Do not invent semantics for an unused template property.

Add a relationship because the note's subject, work, evidence, membership, or actual dependency supports it.
Assess that relationship while deciding the home, not during a later indiscriminate linking pass.
Do not link every note to every sibling, paint, artwork, or project.
Retain independent identities that merely have similar names.

## Make the proposal reviewable

Show the before and after paths, role decisions, frontmatter changes, and intended exact targets.
Include incoming-link effects beyond the source folder when a rename can change them.
Identify expected topic, project, collection, and inventory views without forcing every note into every view.
Follow the vault's diff-review rule.
If the user already authorized the specific work, proceed after the required preview without another permission question.
