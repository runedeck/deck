# Obsidian workflow

Use this procedure for authorized Obsidian collection work and validation.
It retains Art's image classification and gallery responsibilities.

## Use the shared organization workflow

Load the installed `Obsidian` skill when placing notes, cleaning frontmatter, separating work from resources, or checking link identity.
Its source lives in Deck's `obsidian` module. Discover it through the active skill catalog or configured Deck source.
Deploy the Art and Obsidian modules together when that integration is needed.
Do not assume a personal path, cross-module relative link, or undeclared CLI wrapper.

Obsidian owns the scoped audit, purpose and placement records, duplicate identities, safe migration, and layered validation.
Art supplies verified asset categories, creator roles, palette evidence, subject variants, and gallery expectations.
PaletteCritic still returns independent findings and does not write collection notes.
Keep a painting project, reusable resource, topic, guide, artwork, and paint inventory distinct where those roles apply.
Assess meaningful links while each note finds its home.

If the shared skill is unavailable, preserve completed art work and report that organization guidance is unavailable.
Do not claim the shared workflow ran or install it without authorization.
The following Art-specific checks remain available for a bounded collection correction.

## Discover supported access

Confirm the target vault, running application state, dedicated CLI, and current supported commands.
Read the installed CLI's help before selecting read, search, property, link, or validation commands.
CLI capabilities vary by version. Use only commands supported by that installation.
Prefer the dedicated CLI for application-backed validation and available file tools for scoped text changes.

On macOS, the demonstrated dedicated launcher is:

```text
/Applications/Obsidian.app/Contents/MacOS/obsidian-cli
```

Confirm that it exists before use. A different installation can have a different supported launcher.
Do not substitute the Obsidian GUI executable as a command-line probe.
Previous GUI-binary probes aborted during macOS application registration.
That evidence concerned failed child processes and did not prove that the already-running window crashed.

## Make and verify scoped changes

Read the current collection and logging standards before editing.
Prepare coherent note, asset, property, and Base changes within the authorized scope.
Validate file syntax and relative or wiki links, then verify the application can read the changed records.
Check application search or metadata results for the edited paths and relevant category properties.
Inspect affected Base filters and thumbnails, including subjects with multiple evidence types.

Use the shared workflow's separate content, relationship, view, and requested visual reports.
Record which layer succeeded:

```text
Files: changed text, properties, local assets, and CLI readback are consistent.
Relationships: exact topic, project, reference, and collection destinations are correct.
Views: actual category filters and embedding contexts show the intended records.
Visual: the requested GUI inspection shows the intended gallery and notes.
```

Do not infer relationship, view, or visual success from file checks alone.
Keep category flags, thumbnails, attribution, and uncertainty fields during frontmatter cleanup when they carry meaning or serve gallery filters.
Report targeted validation separately from full-vault diagnostics.
An unrelated global warning does not justify rewriting unaffected notes.

## Inspect the GUI when requested

Use Computer Use for the user's requested visual sorting or rendered-view check.
Acquire fresh application state after navigation and each material UI change.
Open the intended note or gallery and confirm its visible identity before editing or classifying it.
Inspect category thumbnails and displayed membership, not just the sidebar or file existence.
A stale screenshot, stale accessibility tree, or unchanged note text does not establish the current rendered result.

Reduce simultaneous gallery embeds when evidence shows excessive rendering work.
A single selectable gallery can be a useful layout correction.
Do not treat that change as proof of a crash cause or apply global settings changes without relevant authorization.

## Handle failures without repeated launches

Distinguish missing executable, timeout, startup failure, nonzero status, and termination by signal.
After a signal failure, stop repeated probes and retain the exact invocation and failure evidence.
Inspect relevant crash logs before diagnosing the cause.
Do not start the GUI binary, reinstall plugins, or change application settings as an automatic fallback.

Preserve completed file changes and state which application validation remains unavailable.
When the user requested diagnosis, investigate the failing launcher and related logs within that scope.
Otherwise, finish the supported collection work and report the narrow validation limitation.
